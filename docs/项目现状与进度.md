## 0. 一句话定位

一个**完全本地离线**的《艾尔登法环》攻略 RAG 问答系统。核心卖点不是「接了个向量库」，而是：

> **逃课打法这类知识只存在于玩家社区、不在 wiki 上**，所以我把「wiki 通用攻略」和「人工整理的逃课/常规打法」拆成三层独立索引，用规则路由 + 三路召回 + 实体硬置顶做融合，把短问句召回准确率从 15.5% 提到 98.6%。

## 2. 架构与关键设计决策

```
用户提问
   │
   ├─ 规则路由 route()          → intent: cheese / brain / level / knowledge / normal
   │                              → 三层权重 (w_l1, w_l2, w_l3) + 等级上限
   ├─ 查询增强 enhance_query()   → 「玛莲妮亚怎么打」→「玛莲妮亚 Malenia 怎么打」（只喂 embedding）
   │
   ├─ 三路召回（每层独立查，避免 L1 的 8 千条挤掉 L2 的 55 条）
   │     L1 纯向量 top-12
   │     L2 向量 + 结构化过滤 + 实体命中打分
   │     L3 同上
   │
   ├─ 加权融合 + 实体硬置顶 → Top-6
   │
   └─ core/qa.py 组装 Prompt → Ollama 流式生成（失败则降级为纯检索原文）
```

**六个我认为值得被审阅的设计点：**

1. **三层分库而非单层混合**：L2/L3 语义上与「怎么打」的主流段落并不相似，混在一层会互相淹没。分层后按意图分配权重。
2. **实体命中是「硬规则」不是软加成**（`_entity_hit()`）：实测「大树守卫怎么逃课」与目标条目的向量相似度只有 0.299，而正文里沾边的无关条目能到 0.63——调权重救不了这个量级差，只能按实体直接分级置顶（exact 全名 2.0/1.5，suffix 后缀 1.5/1.0，按命中长度分档）。
3. **否定词表优先于关键词**：「怎么打**不逃课**」里含「逃课」二字，纯关键词会判成想逃课。
4. **查询增强只喂 embedding，不参与实体匹配和路由**：增强注入的英文名会把原词插断（「黑剑眷属」→「黑剑 black blade眷属…」），实体匹配必须用用户原话。
5. **降级策略**：LLM 挂了直接返回检索原文的结构化摘要——检索层才是核心资产，宁可不给模型润色，也不能让它编。
6. **打包时数据与程序分离**：exe 只有代码和依赖，`data/ models/ .vectorstore/` 外置，改攻略后双击「更新攻略.bat」重建索引（68 秒），不需要重装 Python、不需要重新打包。

## 3. 检索质量评估（2026-09-10 复跑，非历史数据）

评估集：`data/elden_ring/eval_set.json`，71 条人工标注问法，分 7 组。
判定标准：Top-K 中同时命中「期望层 + 期望目标」才算对。

| 方案 | Hit@1 | Hit@5 | MRR | 层准确率@1 |
|---|---|---|---|---|
| A 单路纯向量（基线） | 15.5% | 23.9% | 0.190 | 35.2% |
| B + 术语增强 | 15.5% | 21.1% | 0.178 | 16.9% |
| C + 分层加权 | 21.1% | 31.0% | 0.242 | 57.7% |
| **D + 实体命中（线上方案）** | **98.6%** | **100%** | **0.991** | **97.2%** |

分组表现（D）：逃课 23/23、常规 22/22、否定表达 8/8、知识问答 6/7、无脑度 5/5、等级过滤 5/5、口语俗称 1/1。

**两个我不藏的疑点（希望审阅者给判断）：**

- **B 比 A 还差**：术语增强让 MRR 0.190→0.178、层准确率 35.2%→16.9%。我的解释是「注入英文名提升了 L1 跨语言匹配，但同时把 L2/L3 人工条目挤下去了」，但没有单独做 L1-only 的对照实验来证实。
- **D 的 98.6% 是否存在乐观偏差**：评估集是我自己写的、与 L2/L3 同源（我知道库里有什么才写的问题），而实体命中是硬规则。真实泛化能力应该用**盲测集**（别人出题）来验。

## 4. 工程化与交付

| 项 | 说明 |
|---|---|
| 打包 | PyInstaller 6.22 onedir；`scripts/package_win.py` 一键构建 + 复制外置数据 + 体积报告 |
| 产物 | `dist/NaviRAG/` 1.6 GB（exe 75.9 MB + 依赖 ~850 MB + 模型 458 MB + 向量库 192 MB），Release zip **956 MB** |
| 更新机制 | `NaviRAG.exe --rebuild` → md → jsonl → 全量重建索引（68 s，实测通过）；日志落 `update_log.txt`（打包版无控制台） |
| 踩过的坑 | ① chromadb 用 `importlib` 动态加载实现类，PyInstaller 静态分析漏收 `chromadb.telemetry.product.posthog`，运行时崩 → spec 必须 `collect_submodules('chromadb')`；② 打包后 `__file__` 指向临时目录，数据路径必须基于 `sys.executable` 定位 |
| 依赖外部 | **Ollama 是硬依赖**，演示机必须装并拉 qwen3:8b；exe 只解决 Python 环境问题 |

## 5. 已知问题与风险（诚实清单）

| 级别 | 问题 | 现状 |
|---|---|---|
| 高 | 人工数据规模小：L2 55 条（覆盖 50 个目标）、L3 30 条（覆盖 30 个目标） | 平均每个目标只有 1 条打法，评估指标高，但覆盖广度撑不起「游戏攻略助手」的定位 |
| 高 | 评估集与知识库同源、自标自评 | 存在乐观偏差，缺盲测集 |
| 中 | 实体命中与路由都是**硬编码规则 + 关键词表** | 换游戏/new boss 需要重写词表，泛化性存疑 |
| 中 | 无单元测试、无 CI | 只有冒烟脚本和检索评估脚本 |
| 中 | README / docs 数字与仓库实际对不上 | README 称术语表 15,751 条（对齐条数，去重前），实际参与检索的去重映射 `glossary_flat.json` 是 **10,129** 条，表述易被误读；`docs/eval.md` 里 A 方案 MRR 曾记 0.188 / 层准确率 36.6%，本次复跑为 0.190 / 35.2%（已同步） |
| 中 | 术语增强在消融中**负收益**，但线上仍开着 | 缺乏分层的对照实验支撑 |
| 低 | README 定位语「无 GPU、纯 CPU」与特性栏「本地 GPU 推理」表述矛盾 | 实际是：embedding 走 CPU（torch 2.14.0+cpu），LLM 走 Ollama 的 GPU |
| 低 | 索引更新是全量重建（68 s）而非增量 | 数据量翻 10 倍后不可接受 |
| 低 | 单进程单用户、无并发/鉴权 | 定位是本地工具，暂不算缺陷 |

## 8. 复现方式

```bash
# 环境：Python 3.13 + Ollama（需 ollama pull qwen3:8b）
pip install -r requirements.txt

# 重建数据（README 快速开始 6 步）
python scripts/build_glossary.py && python scripts/fetch_wiki.py
python scripts/build_l1_zh.py && python scripts/clean_l1.py
python scripts/build_l2.py && python scripts/build_l3.py
python scripts/download_model.py

# 检索自测 / 评估复跑 / 界面
python -m core.retriever "玛莲妮亚怎么打"
python scripts/eval_retrieval.py          # 输出第 3 节那张表
streamlit run app.py                       # 网页端
python desktop_chat.py                     # 桌面端
```

打包：`python scripts/package_win.py`（需 PyInstaller，首次约 8 分钟）。
